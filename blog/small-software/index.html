Small software

September 10, 2026 · spawnpoint

Most of the software you use every day is enormous. It has a login page that took a team a quarter, a settings screen nobody finishes, and an on-call rotation. That is big software, and the world runs on it.

Most of the software people actually need is not like that. It is the on-call rota for six people. The form that files a request into a spreadsheet. The page with one live number on it that the whole team looks at in the morning. The tool someone built on a Saturday that quietly became how the department works.

We call that small software. Here is the definition we build against.

The definition

Small software is a program one person can hold in their head, that does one job for a few people, and that is cheaper to rebuild than to explain.

Four properties, and each one changes how the thing should be built.

One job. A tracker, a form, a dashboard, a bot. Not a platform. When a program does one job, its whole shape is visible: there is nothing to configure, no admin panel, no plugin system. The job is the spec.

A few people. Tens, not millions. Everyone who uses it could fit in one room, and usually does. That is not a limitation to grow out of. It is the reason the program can be small: no scale to plan for, no ops to staff, no abuse to defend against, no one to onboard.

Held in one head. It fits in one file, or a handful. One person can read all of it in an afternoon and understand what it does. When it breaks, the person who fixes it does not need a runbook.

Cheaper to rebuild than to explain. This is the new one. If the whole program can be regenerated from a paragraph, then the paragraph is the source of truth and the code is a build artifact. You do not refactor a build artifact. You rebuild it.

Where it went

Small software used to be everywhere. Excel macros. A PHP file on shared hosting. An Access database on the shared drive. A cron job with a Perl script behind it. They were not pretty, and they were not "engineering", and they ran whole companies.

Then hosting became a discipline. The industry built extraordinary tooling for big software: container orchestration, service meshes, deployment pipelines, observability stacks. All of it correct for big software, and all of it a tax on small software. Putting a page online stopped being "FTP the file" and became a project with a cloud account, a build step, a secrets manager, and a Dockerfile. Writing the tool took an afternoon; running it took a week and a credit card.

So small software went back to spreadsheets, and the spreadsheets got worse, because the person who should have written a small program was told that programs are a big deal.

What agents change

An agent writes small software in minutes. Not big software, not yet: the things an agent writes well today are exactly the one-job, one-file programs that fit in one head. The cost of writing small software has dropped to roughly the cost of describing it.

That leaves the last mile, and the last mile is everything the hosting discipline made expensive:

  • Putting it online, with a link that does not change.
  • Keeping its data between versions, so a redeploy does not wipe the notes.
  • Letting three coworkers open it, and nobody else.
  • Giving it a model to call, without signing up at a model provider.
  • Turning it off when nobody is using it, so it costs nothing.

That list is the product, and the parts of it that are not built yet are the roadmap. Today: one call from the agent, and the small program is a link that does not change. Sharing works like a document: type an email, that person can open it. Idle, it sleeps and costs nothing. Next: a data directory that survives every redeploy, a database when the program asks for one, and a model endpoint already waiting in its environment. We will write about each of those here as it lands.

What small software is not

It is not a toy. A tool four people use every day is worth more than a platform nobody logs into, and most of the software that runs a business is exactly this size.

It is not a prototype. A prototype is a small version of a big thing you intend to build. Small software is the finished size. It never needed to be bigger.

It is not simple. One job can be a hard job. Small is about scope and audience, not difficulty.

The rules, short

  • One machine, one process.
  • One directory of data. A SQLite file is a fine database.
  • One model call away, when it needs one.
  • A link you can share with a person, not a deployment you hand to a team.
  • Rebuild it before you refactor it.
