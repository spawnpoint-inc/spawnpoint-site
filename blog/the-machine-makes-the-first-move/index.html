The machine makes the first move

October 7, 2026 · spawnpoint

What a deploy is

spawnpoint is a deploy tool for AI agents. An agent calls one MCP tool, deploy_project, with a bundle of files and a runtime. spawnpoint boots a small virtual machine, puts the files on it, installs dependencies, starts the app, and hands back a public URL. That middle step, putting the files on the machine and running things there, is the part this post is about. The machine boot and the dependency install are the same either way.

How the push worked

Until this week the control plane reached into every machine over SSH, through the machine provider's SSH proxy. It worked, and it shaped the whole deploy path around the proxy's quirks:

  • The key had to land first. A new machine accepts the deploy key only once the provider has written it into place, which took anywhere from one to six minutes after the machine reported ready. The push retried a dial every ten seconds until it got in.
  • No stdin. The proxy dropped standard input, so file bytes could not be streamed. They rode inside the command line instead: one gzipped tar split into 16 KiB chunks, each chunk its own SSH command writing its own part file, then an extract. A 4 MB app was about 260 commands.
  • Dropped sessions. Early sessions were cut off by the proxy, so every command had to be safe to run again, and a session that wedged needed a deadline of its own.
  • Reaching in. The control plane held a private key that opened every customer machine, and a deploy was a goroutine that lived past the request that started it, for the minutes the push took.

Each of those had a fix, and the fixes were correct. They were also most of the 970 lines of internal/sshpush, and for the months the control plane ran on a droplet, the key wait was most of what a user saw while watching a first deploy.

How the agent works

Now the machine makes the first move. A new machine boots with a short startup script that installs spawnpoint-agent, a static Go binary under seven megabytes. The agent exchanges a one-time boot token for its own credential and then asks the control plane for work, holding each request open for 25 seconds and asking again.

A job is a script and what the script needs on disk: the app's files as one gzipped tar the agent fetches and checks against a hash, a few extra files written straight into the job directory, and the app's environment. The script is the same shell the push used to run command by command, rendered as one file. It stages the files, swaps them into place, installs, starts, and confirms, and on a failed update it puts the previous version back. The agent runs it, reports each step as it completes, and posts the exit status. Then it asks for more work, for the life of the machine.

What that changes:

  • One fetch instead of hundreds of commands. The bundle is one HTTPS GET on the machine's own network. A 4 MB app takes about as long as a 4 KB one, and the gap grows with the bundle.
  • Nothing reaches in. The control plane never connects to a machine. There is no deploy key, no retry loop, no chunking. A failure is a script exit with its output attached, not a dropped session to interpret.
  • Nothing depends on the proxy's mood. The push's one-to-six-minute key wait, its dropped early sessions, and its 35,000 byte packet ceiling were all properties of reaching in from outside. A process already on the box has none of them, wherever the control plane happens to run.

The numbers

One Flask app with a requirements.txt (one real dependency to install), a SQLite file in the persistent data directory, and padding files to reach three bundle sizes. Five fresh deploys per size, each under a new name so the whole path is paid, then one redeploy of each in place, then terminate. The clock is the client's: it starts before deploy_project is called and stops when watch_deploy reports the app live. Both runs were on production, on the same account, at night.

Fresh deploy, seconds to live, median (min to max):

Bundle SSH push Pull agent
4 KB 70 (64 to 83) 70 (67 to 70)
512 KB 70 (67 to 73) 70 (67 to 74)
4 MB 93 (84 to 108) 72 (72 to 72)

Redeploy in place, seconds to live, median (min to max):

Bundle SSH push Pull agent
4 KB 16 (16 to 21) 21 (21 to 21)
512 KB 24 (18 to 24) 22 (16 to 22)
4 MB 37 (37 to 38) 22 (18 to 25)

Where a fresh deploy's time goes, median seconds from the call, 4 KB and 4 MB bundles:

Step SSH, 4 KB Agent, 4 KB SSH, 4 MB Agent, 4 MB
Machine reports running 12 12 14 14
Files start landing on the machine 40 41 42 43
App live on its URL 70 70 93 72

Both paths wait the same 12 seconds for the machine and reach it at about the same moment: the agent by its bootstrap, download, and enrolment, the push by waiting for the proxy to accept the deploy key. Then both run the same pip install, about 27 seconds. On a small bundle that is the whole story, and the two tie. On a 4 MB bundle the push spends 20 to 30 extra seconds moving bytes as 16 KiB commands, and the same 15 seconds again on every redeploy; the agent's single fetch does not register.

One thing we expected to see and did not: the one-to-six-minute key wait that shaped the push's design. When the control plane moved from a DigitalOcean droplet to AWS last week it landed in the same region as the machine provider's proxy, and the wait went from minutes to about 25 seconds. Had we measured on the droplet, the agent would have won by minutes on every cell. We did not, so this post says what we measured.

What did not change

The deploy's rules are the same. A terminate that lands mid-deploy wins. A machine that is serving is never reaped. A failed update puts the previous version back and the project stays running with the error recorded. The runtime commands, the unit file, the staging swap, sleep and wake, the gate, custom domains, and every MCP tool's shape are untouched. The script the agent runs is composed from the same pieces the push ran, so a fix to how a runtime installs or starts is one edit either way.

What it cost

A root process on every customer machine, which is the one place the "plain Ubuntu, nothing of ours on the box" rule bends. It bends on purpose: the agent is a runner, not an executor. It knows how to prepare a directory, run a script, stream its output, and report the exit. Every line of deploy logic stays on the control plane, where it has its tests. The agent never needs to change when a runtime does.

And one hour-long detour on the first production run: the job directory was created root-only, and the script re-executes itself as the app user, who could not reach it. The failure path did exactly what it should (the project went to error, the machine was reaped), the fix was one permission bit, and the second run went through.

Method, for the record

The harness is cmd/spawnbench in the spawnpoint repo. It deploys through the public MCP endpoint the way any agent would, stamps each progress step as it arrives, and writes one JSON line per deploy. The transport is a setting on the control plane, so the comparison is two runs with the box flipped in between. Machine allocation is the provider's and varies from run to run; that is why there are five per cell and the min and max are shown. The SSH numbers are what the push did on 2026-10-07 from the AWS control plane; they include the provider's key propagation, which is real time a user waited, not a flaw in the measurement. The raw rows are in the repo under docs/benchmarks/.
