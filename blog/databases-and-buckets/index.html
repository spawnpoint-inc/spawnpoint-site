Your apps can now have a database and a bucket

October 9, 2026 · spawnpoint

A spawnpoint project can now have its own Postgres database and its own S3 bucket, a container for files in Amazon's storage service. You ask your agent, the agent makes one call, and the app restarts with the connection details in its environment.

Until now, an app kept its data in a folder on its own machine. That still works, and for most small apps it is enough. But the folder goes away with the machine, and every photo a guest uploads has to pass through the app. A database and a bucket live off the machine, and no other project can reach them.

Which one to use

Every project already has a data directory on its machine. The app finds its path in SPAWNPOINT_DATA_DIR (/home/ubuntu/data, or /data inside a Docker container). Files written there survive redeploys and sleep. It needs no setup, so it is the right place for a SQLite file, a JSON file, or any file only the app reads. It lives on the machine, though. If the machine is replaced, which happens when it dies or when you change the app's runtime (from Node to Python, for example), the new machine starts with an empty directory.

A Postgres database (add_database) is for relational data that has to outlive the machine: sign-ups, orders, scores, anything you would query. It runs on spawnpoint's managed database server, so a new machine connects to the same data.

A bucket (add_storage) is for files that browsers upload or download: photos, documents, generated images, exports. It also outlives the machine.

If you are not sure, start with the data directory. Move rows to Postgres when losing them with the machine would matter, and move files to a bucket when people upload or download them.

How to add one

Deploy the app first, then ask your agent. For example:

Add a Postgres database to the club-signups project and move the sign-ups out of the SQLite file into it.

Give the photo-wall project a public bucket for the photos, and let guests upload from their phones.

add_database creates the database and sets DATABASE_URL in the app's environment. The app connects with any Postgres client library and creates its own tables. add_storage creates the bucket and an access key for it, and sets S3_ENDPOINT, S3_REGION, S3_BUCKET, S3_ACCESS_KEY_ID, and S3_SECRET_ACCESS_KEY, plus S3_PUBLIC_URL for a public bucket. The app uses any S3 library. If you write that code yourself, pass these values to the S3 client directly: the libraries look for AWS_* names on their own, not these. Either tool restarts the app with the new variables, and they are kept like any other environment variable, so they survive redeploys. Asking twice returns the same database or bucket. If you already set a DATABASE_URL or S3_* variables of your own, the tool refuses rather than overwrite them. The project's page in the console has the same actions as buttons.

Uploads go straight from the browser to the bucket. The app uses its key to sign a presigned URL, a link that lets a browser upload or download one file for a limited time, and gives it to the browser. The browser sends the file to S3 with that link, so the bytes never pass through the app's machine. Agents often write upload code that passes every file through the app, so the tool's description tells them to use presigned URLs instead.

A bucket is private by default: only the app's key can read it, and browsers get presigned URLs. A public bucket is for files meant for everyone, such as a gallery's images. Anyone can read a file in it at S3_PUBLIC_URL/<key>, and S3 serves it without a request to the app. The list of files stays private either way, so a public bucket serves a file only to someone who has its exact name. Ask the agent to make a bucket public or private at any time.

New spawnpoint projects are restricted: only the people you share them with can open them. A public bucket is outside that check. When a change leaves a restricted project with a public bucket, the agent gets a warning to pass on to you. If the files are only for the people you shared the project with, make the bucket private and have the app hand out presigned URLs.

If the bucket's key leaks, for example in a log you pasted into a chat, ask the agent to rotate it. rotate_storage_key creates a new key, checks that it works, restarts the app with it, and only then deletes the old key, so the app never loses access. Presigned URLs signed with the old key stop working.

How each project's data stays its own

Each database has its own user with a long random password, and other projects' users are not allowed to connect to it. A leaked DATABASE_URL reaches that one database and nothing else. Connections are encrypted with TLS, and the server refuses connections without it. Each app can hold up to 20 connections at once, and by default a query that runs longer than 60 seconds is cancelled.

Each bucket has its own access key, and that key's permissions name one bucket and no other. Files are encrypted at rest. The server that runs spawnpoint can list and delete the files in a bucket, which it needs to do to empty a bucket before deleting it, but it has no permission to read or change them.

Removing a database or a bucket deletes its data for good. So remove_database and remove_storage refuse unless the agent passes confirm: true, which it should do only after asking you. In the console, you type the project's name to confirm. Terminating a project deletes its database and its bucket with everything in them, and terminate_project asks for the same confirmation. A scheduled teardown is a terminate, so it deletes them too when it runs. Redeploys, sleep, and a replaced machine leave both as they are.

Plan limits

Each plan sets how large one project's database and bucket can grow:

Plan Database Bucket Live projects
Free 512 MiB 1 GiB 1
Pro, $10 a month 4 GiB 25 GiB Unlimited
Business 16 GiB 100 GiB Unlimited

spawnpoint checks each database's size every hour. A database over its plan's limit becomes read-only, and nothing in it is deleted. To get back under, delete data in a session that first runs SET default_transaction_read_only = off, or upgrade the plan. The database is writable again within the hour.

S3 reports a bucket's size once a day, so a bucket can pass its limit by about a day of uploads before the stop applies. Over the limit, the app's key can no longer upload, and reads, listings, and deletes still work. Nothing is deleted. An upgrade lifts the stop within the hour. Deleted files count once S3's next daily measurement shows the bucket under the limit, which takes up to about a day.

In both cases get_project shows the size, the limit, and whether the database or bucket is read-only, with a note the agent passes on to you.
