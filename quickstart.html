Quick start

From nothing installed to a live URL, entirely on your own machine. About five minutes, most of it waiting on a clone and a boot.

What you need: Go 1.26 or newer, git, and Claude Code. That's it. No account, no cloud provider key, no Docker. spawnpoint runs on your laptop and ships with an offline backend so the whole flow works before you have any infrastructure at all.

1. Start spawnpoint

Clone the repo and run the dev script. Leave it running in its own terminal:

git clone https://github.com/mannanshukla/spawnpoint.git
cd spawnpoint
./scripts/dev.sh

It prints the three URLs it serves, and you should be able to open each one now:

  • http://localhost:8080/ is this landing page.
  • http://localhost:8080/console is your console.
  • http://localhost:8080/healthz answers {"status":"ok"}.
With no OPENRELAY_API_KEY set, spawnpoint runs against its mock backend: deploys succeed instantly and return a simulated URL, so you can walk this whole page offline. Making the links real is one env var, covered at the bottom.

2. Install the plugin

The plugin gives your agent two skills: one to connect, one to ship. Point the marketplace at the repo root you just cloned:

claude plugin marketplace add ~/spawnpoint
claude plugin install spawnpoint@spawnpoint
The one thing people get wrong: the marketplace source is the repo root, where .claude-plugin/marketplace.json lives, not the plugin/ directory inside it. Point it at plugin/ and the install appears to work but the plugin fails to load with cache-miss. Check it with claude plugin marketplace list: the source should read Directory (/Users/you/spawnpoint).

3. Point Claude Code at your local server

The plugin ships the skills; this line is what actually wires up the connection:

claude mcp add --transport http --scope user spawnpoint http://localhost:8080/mcp

No token and no header: authentication happens in the browser in the next step. --scope user makes spawnpoint available in every project; --scope project limits it to this one. If you would rather not run it yourself, say "set up spawnpoint" and the setup skill runs it for you.

4. Restart Claude Code, then sign in

  1. Restart Claude Code so the new skills and the MCP connection both load.
  2. Run /mcp, select spawnpoint, choose Authenticate. Your browser opens http://localhost:8080/console/login.
  3. Enter any email address. Nothing is sent: in local dev the magic link is printed straight onto the page. Click it.
  4. You land on the consent screen. Click Approve.

Claude Code stores the tokens itself, in your OS keychain, and refreshes them automatically. This is a one-time step and there is no key to copy anywhere.

5. Deploy something

Now just talk to your agent:

"build me a countdown timer page and deploy it to spawnpoint"

You get a URL back within a few seconds with status spawning. The app finishes provisioning in the background and the link goes live shortly after. To check the wiring without building anything, ask your agent to list your spawnpoint projects: if that returns without an auth error, you are connected.

6. Watch it, then take it down

Open http://localhost:8080/console. Your project is listed with a status pill that flips from Spawning to Running on its own; the page polls, so you do not need to reload. Each project has its live link, who you have shared it with, and a Terminate button that stops the machine and frees the URL. Your agent can do the same thing if you ask it to take the project down.

What actually happened

Your agent called the deploy_project tool over MCP with the files it wrote. spawnpoint booted a small VM, returned its public URL immediately, and then in the background pushed the files onto the machine over SSH and started the runtime's server on port 8080, which the public URL proxies to. There is no container, no registry, and no image build in the path. spawnpoint itself never leaves your laptop: only the deployed app runs remotely.

Supported runtimes

  • static is the default: your files served over HTTP.
  • node runs your entrypoint (default index.js) with PORT=8080.
  • python runs your entrypoint (default main.py) with PORT=8080.

Making the links real

Everything above works against the mock backend. To deploy to actual VMs, drop an OpenRelay API key into .env at the repo root and restart the server:

echo "OPENRELAY_API_KEY=vl_your_key_here" >> .env
./scripts/dev.sh

On startup you should see openrelay preflight ok and backend=true in the log. Nothing else about the flow changes. VMs bill by the hour, so terminate the projects you are done with; a deploy that fails reaps its own VM automatically.

Connecting without the plugin

Any MCP client works, since the plugin is only a convenience. Point one at your local server over Streamable HTTP and it will discover the OAuth flow from the endpoint itself:

{
  "mcpServers": {
    "spawnpoint": {
      "type": "http",
      "url": "http://localhost:8080/mcp"
    }
  }
}

Clients that cannot do OAuth (a shell script, a cron job, CI) can use a long-lived spk_live_ token instead: create one in the console and send it as Authorization: Bearer.

If something goes wrong

  • Connection refused, or /healthz fails: the server isn't running. Start ./scripts/dev.sh and leave that terminal open.
  • Plugin failed to load: cache-miss: the marketplace points at the wrong directory. Run claude plugin marketplace remove spawnpoint, then add the repo root instead of plugin/.
  • The deploy_project tool is missing: you have the skills but no MCP connection. Re-run the claude mcp add line from step 3, then restart.
  • 401 or unauthorized: the grant expired or was revoked. Run /mcp, pick spawnpoint, and choose Authenticate again.
  • No browser opens: confirm the server is reachable at http://localhost:8080/healthz, then retry Authenticate.
  • Sessions drop after a restart: expected in dev. SESSION_SECRET is random on every boot unless you pin it in .env.
